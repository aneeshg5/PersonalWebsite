# ForeTrack4D — Single-Image 3D Motion Forecasting for Hand-Held Objects

**Type:** Personal Research Project
**Categories:** Computer Vision, 3D Perception, Generative Models
**Stack:** Python, PyTorch, CUDA, ViT, Diffusion Transformers, SAM 2, TAPIP3D, MegaSaM, OpenCV, NumPy
**GitHub:** https://github.com/aneeshg5/ForeTrack4D

## Overview

ForeTrack4D answers a question you can pose from a single photograph: given one RGB frame of a person holding an object, where is that object about to go in real, metric 3D space? The model takes that single frame plus 64 query points on the object's surface, and predicts a full trajectory for every one of those points across 128 future timesteps — a (128, 64, 3) tensor of world-space coordinates, expressed in the camera frame at the moment of prediction. The output is 3D point tracks, not pixels; this is explicitly not video generation. Because the future of a manipulated object is genuinely ambiguous (a box being lifted could go up, sideways, or toward the camera), the forecaster is a conditional diffusion model rather than a regressor, so it can represent a distribution over plausible futures instead of collapsing them into a single blurred average.

## Motivation and the Gap It Fills

The direct inspiration is ForeHand4D (Prakash, Forsyth and Gupta, arXiv:2510.06145), which forecasts bimanual hand motion and articulation from a single everyday image, and which names object motion forecasting as future work rather than solving it. ForeTrack4D is that follow-on. Hands are an easier target than objects in one specific way that matters: a hand has a fixed, known kinematic structure (MANO), so the model predicts a small fixed parameter vector. An arbitrary manipulated object has no canonical parameterization at all — it could be a mug, a drill, or a bag of chips. The design decision that makes the transplant work is to drop the parametric model entirely and forecast raw 3D point tracks on the object surface, which is a representation that is agnostic to object identity, shape, and topology. That choice also brings a second problem into scope, since no large in-the-wild dataset carries ground-truth 3D object trajectories, which is what motivates the pseudo-labeling half of the system.

## Model Architecture

The denoiser is an MDM-style transformer encoder with 16 layers, 4 attention heads, and a latent dimension of 1024, matching the ForeHand4D paper's stated denoiser spec so the comparison stays honest. Each of the 128 forecast timesteps is one token: the noised 64x3 coordinates are flattened to 192 dimensions and linearly projected into the latent space, deliberately mirroring ForeHand4D's 198-dimensional per-timestep hand token so the training loop needed minimal surgery. Conditioning comes from two sources. A ViT image encoder, initialized from HaMeR weights, produces patch features for the single input frame. Then each of the 64 query points contributes its own conditioning token built by concatenating a Fourier positional embedding of the point's 3D position at t=0 with the ViT patch feature sampled bilinearly at that point's 2D projection, so the model knows both where in space and where in the image each track slot lives. The whole query-token block is dropped with probability 0.1 during training as conditioning dropout. The output head predicts an offset from the known t=0 position rather than absolute coordinates, with a zero-initialized projection, which makes "the object does not move" a free and stable thing for the network to express early in training.

## Diffusion Setup and Loss

Diffusion runs over 1000 denoising steps on a cosine noise schedule, predicting x0 directly rather than the noise, following MDM's convention for motion data where x0 prediction is empirically better behaved than epsilon prediction. The training loss is an L2 on coordinates scaled by inverse depth per point per timestep, an idea borrowed from TAPIP3D's depth-adaptive weighting: without it, points far from the camera carry disproportionate absolute error in meters and dominate the gradient, even though their pixel-space and perceptual error is small. Coordinates are normalized by per-dataset translation mean and standard deviation computed over the training tracks, since DexYCB tabletop distances and egocentric H2O distances occupy very different ranges and a single global normalization washes out the closer dataset. At inference the sampler draws 5 futures per input, which is what makes the diversity and multimodality metrics meaningful.

## Ground-Truth Track Generation

For the lab datasets there is no existing 3D track annotation, so ground truth had to be synthesized from what those datasets do provide: per-frame 6DoF object poses, object meshes, and calibrated cameras. The pipeline farthest-point-samples 64 points on the manipulated object's mesh surface in its canonical frame, transforms them by the per-frame object pose into the camera frame, and treats the t=0 camera frame as the world frame. Per-point visibility is computed by rendering the mesh with a z-buffer offscreen and marking a point visible when its projected depth agrees with the rendered depth to within 5 millimeters, so occlusion by the hand is handled correctly rather than assumed away. ARCTIC required a specific correction: its objects articulate with a base part and a moving part carrying separate poses, so a single rigid transform per frame is simply wrong, and points must be transformed by the pose of the part they were sampled from. Everything serializes to one npz per sequence with tracks, visibility, intrinsics, image paths and object id, and a sanity harness reprojects the generated tracks back onto video for visual verification before any training run.

## Pseudo-Labeling Pipeline for In-the-Wild Video

Lab datasets are clean but small and visually narrow, so scaling to real footage required generating 3D labels where none exist. The pipeline chains three separate pretrained systems per clip. SAM 2 segments the manipulated object at the query frame, seeded from detected hand keypoints near the contact region, taking the largest coherent non-hand mask; this component needed real debugging, because naive best-score mask selection kept returning slivers of the object that placed all 64 query points on a handful of pixels straddling a depth discontinuity. MegaSaM then recovers metric depth and camera poses for the monocular clip, and TAPIP3D tracks the query points through the full clip in persistent world space. Quality gates then reject entire clips rather than individual points when the median frame-to-frame jerk exceeds a threshold calibrated on lab ground truth, when per-point depth variance is extreme (TAPIP3D's documented failure mode is depth flicker on small or distant elements), when fewer than half the frames are visible, or when MegaSaM confidence is degenerate. Accepted clips are written in the exact same npz schema as the lab ground truth with a source field marking them as pseudo, so the dataloader treats both identically.

## Training Recipe

Training deliberately runs in two stages that are never merged, reproducing the ForeHand4D recipe which documented that training from scratch on noisy imputed labels is unstable. Stage 1 trains on clean mesh-derived ground truth from DexYCB, ARCTIC ego, and H2O with augmentation on, using a dataset string mechanism that mixes datasets with per-dataset normalization statistics. Stage 2 loads the Stage 1 checkpoint and finetunes jointly on ground truth plus TAPIP3D pseudo-labels for roughly 20 epochs at a much lower learning rate with gradient clipping enabled, evaluating every epoch. Ablations were run and logged for the decisions that actually needed justifying: query conditioning on versus off (the architecture-justifying ablation, since an image-only model has no way to know which object it is being asked about), depth-scaled loss on versus off, 32 versus 64 versus 128 query points, and 64 versus 128 forecast timesteps. A visibility prediction head with binary cross-entropy was added once the coordinate predictions were healthy.

## Results

On the DexYCB held-out test split with 1,200 evaluation sequences, all figures in centimeters: the static baseline that assumes the object never moves reaches 12.46 ADE and 33.36 FDE, and a constant-velocity baseline given the true second frame (which the model never sees) does no better at 12.52 and 33.40, confirming that this motion is not linearly extrapolable. The same-architecture deterministic regressor reaches 7.85 ADE and 14.50 FDE. The diffusion model reaches 7.43 ADE and 15.91 FDE when the closest of 5 samples is selected against ground truth, and 10.45 ADE and 20.19 FDE for a single unselected sample. The headline improvement is error at the final predicted frame dropping from 33.4 centimeters to 14.5. First-frame-aligned (M-F) and globally-aligned (M-G) variants are reported alongside raw error following ForeHand4D's protocol, because single-image metric depth is scale-ambiguous and alignment is what separates motion-shape error from absolute placement error. On diversity, measured as mean pairwise L2 between predicted motions across the dataset, the model produces 12.97 against a ground-truth spread of 12.15 in domain, meaning the generative distribution is well calibrated rather than artificially wide or collapsed.

## Honest Limitations

The results section of the repository states failures plainly rather than burying them, which was a deliberate choice. Out of domain, the static baseline wins: on HoloAssist the model reaches 8.49 against static's 5.32, and on zero-shot EgoExo4D it reaches 23.83 against static's 19.76. That means ForeHand4D's own headline claim, that imputed pseudo-labels improve zero-shot generalization, does not reproduce for objects at this pseudo-label scale of 213 accepted clips, versus the paper's full HoloAssist and AssemblyHands corpora. The dataset diversity metric shows why: out of domain the predicted spread collapses to 0.97 against a ground-truth spread of 33.30, meaning all five samples become nearly identical. Diffusion also does not beat the plain regressor on single-sample accuracy, so its measurable advantage is the calibrated output distribution plus best-of-5 performance when a downstream selector exists. The out-of-domain evaluation sets are small (43 and 25 sequences) and those rows are directional only, and there is no published-method baseline to compare against since none exists for this exact task.

## Engineering Challenges

The system spans three mutually incompatible Python environments that cannot be unified, since TAPIP3D's xformers, torch-scatter and MegaSaM stack conflicts directly with the training environment's torch build and with SAM 2's dependencies. They communicate by subprocess invocation and npz files on disk, with the expensive MegaSaM depth pass cached so reruns skip it. Several failures were environment-level rather than model-level and had to be diagnosed on shared cluster hardware: compiled CUDA extensions built on one node failed on another with a GLIBCXX version mismatch, resolved by pinning a newer libstdc++ through a separate conda prefix on the library path; cuDNN handle creation failed on one node while plain CUDA worked, resolved with an environment flag that disables cuDNN for convolutions; and MegaSaM out-of-memory errors were resolved by shortening clip length and enabling expandable CUDA allocator segments. One GPU turned out to have uncorrectable DRAM ECC errors with remapped rows pending, which is a hardware fault rather than anything fixable in code.

## Visualization and Demo

A composite renderer produces the forecast-versus-reality comparison shown in the repository README. It plays the real video on one panel while a second panel freezes at the conditioning frame and overlays the model's predicted point trajectories against what actually happened, with a live error-versus-horizon chart scoring the forecast against the static baseline underneath. Getting this honest required a specific correctness fix: because all tracks live in the camera frame at the conditioning moment, observed tracks must not be drawn over later frames of a moving egocentric camera, so the renderer carries an explicit static-camera flag and shows the overlay comparison only on the frozen panel for head-mounted footage. There is also an asynchronous demo application where a user uploads a short single-shot hand-object video, the backend runs the full MegaSaM and TAPIP3D observation pass plus the forecaster from a chosen conditioning frame, and the result page renders the same comparison, with honest rejection messages when the input violates the pipeline's assumptions.

## Technical Stack

| Layer | Technology |
|---|---|
| Forecasting model | PyTorch, MDM-style transformer encoder (16 layers, 4 heads, 1024-dim latent) |
| Image conditioning | Vision Transformer encoder initialized from HaMeR weights |
| Generative framework | Conditional diffusion, 1000 steps, cosine schedule, x0 prediction |
| Segmentation | SAM 2 (Segment Anything 2), hand-keypoint-seeded prompting |
| 3D pseudo-labeling | TAPIP3D for persistent-world point tracking, MegaSaM for monocular depth and pose |
| Ground-truth generation | Offscreen mesh rendering with EGL, z-buffer visibility, farthest-point sampling |
| Datasets | DexYCB, ARCTIC, H2O for ground truth, HoloAssist for pseudo-labels, EgoExo4D for zero-shot evaluation only |
| Training infrastructure | Multi-GPU BF16 mixed precision on L40S and A40 class hardware |
| Visualization | OpenCV, Matplotlib, custom composite video renderer |
